# NNUE v4 訓練可行性深度分析

本報告對 `d8` 代理人的 NNUE 從頭訓練方案進行全面的技術評估，涵蓋架構規格、參數量、數據需求、學習範式以及過擬合/欠擬合防禦策略。

---

## 1. 目前架構與參數量分析

### 1.1 網路層結構（由 C++ 硬編碼，無法修改）

```
┌──────────────────────────────────────────────────────────────────┐
│ Feature Transformer (FT)                                         │
│   Friend FT:  49,216 features → 256 dim (HalfKA, us-perspective)│
│   Enemy FT:   43,840 features → 256 dim (HalfKA, them-persp.)  │
│                                                                  │
│ 激活: Dual Clipped ReLU                                          │
│   [clamp(us, 0, 127), clamp(-us, 0, 127),                       │
│    clamp(them, 0, 127), clamp(-them, 0, 127)] → 1024 dim        │
├──────────────────────────────────────────────────────────────────┤
│ L1: Linear 1024 → 16   + Dual Clipped ReLU → 32                │
│ L2: Linear 32 → 32     + Clipped ReLU → 32                      │
│ L3: Linear 32 → 1                                               │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 精確參數量統計

| 層 | 維度 | 可訓練參數量 | 佔比 |
| :--- | :--- | ---: | ---: |
| Friend FT embedding | 49,216 × 256 | 12,599,296 | 52.8% |
| Friend FT bias | 256 | 256 | ~0% |
| Enemy FT embedding | 43,840 × 256 | 11,223,040 | 47.1% |
| Enemy FT bias | 256 | 256 | ~0% |
| L1 (weight + bias) | 1024 × 16 + 16 | 16,400 | 0.069% |
| L2 (weight + bias) | 32 × 32 + 32 | 1,056 | 0.004% |
| L3 (weight + bias) | 32 × 1 + 1 | 33 | ~0% |
| **總計** | | **23,840,337** | **100%** |

### 1.3 嵌入維度 (VD) 的意義

> **嵌入維度 = 256。** 這是 Stockfish 官方 NNUE 的標準設定。

每個棋盤特徵（「國王在 e1、白兵在 d4」）被表示為一個 256 維的向量。加入這個棋子時，就將其對應的 256 維權重加到累加器上。256 維提供了足夠的表達能力來編碼位置、子力、結構等複雜特徵。

## 2. 現有配置致命問題：數據與參數比

### 2.1 數據量嚴重不足

| 項目 | 目前配置 | Stockfish 官方 | 最低可行門檻 |
| :--- | :--- | :--- | :--- |
| **總參數量** | 23.8M | 23.8M（相同架構） | 23.8M（固定） |
| **訓練數據量** | 270K | **10 億+** | **500 萬 ~ 1000 萬** |
| **數據/參數比** | **0.011** | **42+** | **0.2 ~ 0.4** |

> [!CAUTION]
> **目前的數據/參數比僅為 0.011，即每個參數平均只有 0.011 個訓練樣本。**  
> 這遠低於深度學習的基本要求（通常需要每個參數至少 1-10 個樣本）。  
> 在此條件下，即使使用所有正則化手段，**嚴重過擬合幾乎是不可避免的。**

### 2.2 稀疏性的緩解效應

有人可能會反駁：「NNUE 的輸入極度稀疏（每個局面只激活 ~30 個特徵），所以實際上只有少量參數被更新。」

這確實部分正確：
- 每個局面只更新 ~30 × 256 = 7,680 個 FT embedding 參數
- 但 FC 層的 17,489 個參數在**每個局面都會更新**

然而，問題在於**覆蓋率**：
- Friend FT 有 49,216 個特徵，每個特徵需要在**足夠多的上下文**中被激活才能學到有意義的權重
- 以 120K 中局局面、每局 30 個特徵計算，平均每個特徵只被激活 `120,000 × 30 / 49,216 ≈ 73 次`
- 且這 73 次集中在中局（第 16-80 步），根本不涵蓋開局（第 0-15 步）的國王/兵結構

### 2.3 合成數據的局限性

| 合成數據類型 | 問題 |
| :--- | :--- |
| 端局合成（K+Q vs K 等）| 子力計數值是正確的，但缺乏位置理解（如 K+Q 在中心 vs 角落的區別） |
| 開局突變（隨機移除棋子）| 產生的局面在真實對局中不存在，模型學的是「幻想局面」而非真正的西洋棋 |

## 3. v4 方案的預測評估

### 3.1 能解決的問題
- ✅ 開局單調性（兵/馬移除後分數正確方向）
- ✅ 端局單調性（K+Q > K+R > KvK）
- ✅ 消除未訓練特徵的隨機噪聲

### 3.2 無法解決的問題
- ❌ **位置性理解**：模型不知道中心控制、開放線、王安全等概念
- ❌ **兵結構**：不懂孤兵、疊兵、通路兵的價值差異
- ❌ **子力協調**：不懂象對 vs 馬對、雙象優勢等
- ❌ **中局判斷**：120K 中局數據不足以學會可靠的評估
- ❌ **對戰 d6_cpp**：d6_cpp 有手工調製的 PST（Piece-Square Table）、王安全加權和子力獎勵，在位置性判斷上遠超純子力計數

### 3.3 v4 預估對戰結果

| 場景 | 預估 D8 勝率 | 原因 |
| :--- | :--- | :--- |
| **Best case** | 15-25% | 子力計數正確 + 搜尋深度可能略深 |
| **Expected** | 5-15% | 位置判斷弱於 d6_cpp 手工 PST |
| **Worst case** | 0-5% | 中局評估噪聲過大，搜尋效率低 |

## 4. 真正可行的方案

### 4.1 數據需求：500 萬 ~ 1000 萬局面

| 數據來源 | 方式 | 數量 | 品質 |
| :--- | :--- | :--- | :--- |
| **Lichess Elite Database** | 網路下載 PGN → Stockfish 標籤 | 300-500 萬 | ⭐⭐⭐⭐ |
| **Stockfish 自我對弈** | 本地 Stockfish 隨機走子 + 評估 | 200-500 萬 | ⭐⭐⭐⭐⭐ |
| **合成端局** | 本地隨機生成 | 10-20 萬 | ⭐⭐⭐（輔助） |
| **合成開局突變** | 本地隨機生成 | 5-10 萬 | ⭐⭐（輔助） |

> [!IMPORTANT]
> **推薦方案：以 Stockfish 自我對弈（Self-Play）為主，Lichess 實戰為輔。**  
> 自我對弈數據的優勢在於：(a) 每個局面都附帶 Stockfish 的高品質評估；(b) 局面多樣性受控於隨機起始；(c) 可以在 M4 上用低深度（depth 8-10）高效並行生成。

### 4.2 自我對弈數據生成的具體方法

```
1. 以標準起始局面或 Chess960 隨機局面開始
2. 每步讓 Stockfish 以 depth 8-10（或 5000 nodes）搜尋
3. 以 5% 機率隨機走子（增加多樣性），否則走最佳步
4. 每隔 2-4 步保存一個靜態局面（跳過將軍/吃子後的不穩定局面）
5. 保存格式：FEN + Stockfish 評估（centipawns，STM 相對）
```

**時間估算**（M4 Mac，8 核心並行）：
- 每局約 80 步 × 5ms/步 = 400ms/局
- 每局保存 ~20 個局面
- 500 萬局面 ≈ 25 萬局 ≈ 25 萬 × 0.4s ÷ 8 核 ≈ **3.5 小時**

### 4.3 學習範式

> **監督學習（Supervised Learning）** 是正確且唯一合理的選擇。

| 範式 | 適用性 | 原因 |
| :--- | :--- | :--- |
| **監督學習（SL）** | ✅ 推薦 | Stockfish 評估作為標籤，模型學習逼近 Stockfish 的局面判斷 |
| **強化學習（RL）** | ❌ 不適用 | 需要已經能下棋的引擎做基礎，且訓練不穩定 |
| **自監督學習** | ❌ 不適用 | 缺乏西洋棋局面的天然自監督信號 |

### 4.4 防止過擬合與欠擬合的多層策略

| 策略 | 參數 | 防禦目標 | 說明 |
| :--- | :--- | :--- | :--- |
| **充足數據量** | ≥ 500 萬 | 過擬合 | 最根本的解決方案 |
| **FT 小方差初始化** | std = 1e-4 | 過擬合 | 防止未訓練特徵的隨機噪聲 |
| **Weight Decay** | 1e-4 | 過擬合 | L2 正則化，防止權重過大 |
| **學習率衰減** | Cosine Annealing | 過擬合 | 後期降低學習率，避免震盪 |
| **Early Stopping** | Val loss 5 epochs 不降 | 過擬合 | 在最佳驗證損失處停止 |
| **靜態局面過濾** | 跳過將軍/吃子後局面 | 過擬合 | 避免學習戰術噪聲 |
| **充足的 Epochs** | 15-30 | 欠擬合 | 確保模型有足夠的訓練輪數 |
| **適當的學習率** | 1e-3 → 1e-5 | 欠擬合 | 初始足夠大以確保收斂 |
| **Kaiming 初始化 FC 層** | a=0.2 | 欠擬合 | FC 層需要合理的初始化梯度流 |

## 5. 推薦的修正計劃

### Phase 0：數據生成（預計 4 小時）
1. 撰寫 `generate_selfplay_data.py`，利用本地 Stockfish 進行自我對弈數據生成
2. 目標：生成 **500 萬個靜態局面**，格式為 `FEN,score`
3. 過濾規則：
   - 跳過處於將軍狀態的局面
   - 跳過緊接吃子後的局面（非靜態）
   - 分數範圍限制在 -3000 ~ +3000 cp（排除強制將殺）

### Phase 1：訓練（預計 30-60 分鐘）
1. 混合數據集：500 萬自我對弈 + 10 萬合成端局 + 5 萬合成開局突變
2. FT embedding 初始化：`normal(0.0, std=1e-4)`
3. FC 層初始化：`kaiming_uniform(a=0.2)`
4. 優化器：Adam(lr=1e-3, weight_decay=1e-4)
5. 學習率衰減：CosineAnnealingLR(T_max=epochs)
6. 損失函數：HuberLoss(delta=1.0)
7. Epochs：20（含 Early Stopping）
8. 設備：MPS (M4)

### Phase 2：量化與編譯
1. `save_nnue.py` 導出新權重
2. `build.sh` 重新編譯 C++ 引擎
3. 更新 C++ offset 值

### Phase 3：驗證
1. 單調性測試（所有基準 FEN）
2. 對戰 d6_cpp（20 局），目標勝率 ≥ 40%

## 6. 結論

> [!WARNING]
> **目前的 v4 方案以 270K 數據訓練 23.8M 參數的網路，數據/參數比僅為 0.011，嚴重不足。**  
> 雖然可以解決開局單調性問題，但不足以讓 D8 在中局判斷上超越手工 PST 的 d6_cpp。  
> **建議先花 3-4 小時生成 500 萬自我對弈數據**，再進行訓練，這將大幅提升勝率。

| 方案 | 預估勝率 vs d6_cpp | 所需時間 |
| :--- | :--- | :--- |
| v4 原方案（270K 數據） | 5-15% | 30 分鐘 |
| **v4 修正（500 萬數據）** | **40-60%** | **4-5 小時** |
| v4 修正（1000 萬數據） | 50-70% | 8-10 小時 |
